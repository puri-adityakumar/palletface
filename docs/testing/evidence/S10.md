### F-01 — Master qualification status is stale and internally inconsistent (S2, audit gap)

- **Observation:** `docs/testing/MATRIX.md`, `docs/testing/REPORT.md` and `docs/testing/PLAN.md` still state **16/80 approved**, Stage 3 provisional/PENDING, and **55 NOT RUN**. `docs/testing/EXECUTION-LOG.md` records **54/80 approved** after accepting S3-R1, S4, S5, S6-01…08 and S7. `docs/testing/FINDINGS.md` still describes Q-003 as “CONFIRMED” and Q-002 as the current open issue without recording the `f1e17d0` fix/recheck.
- **Evidence:** `out/qualification/S10/audit.json` checks `A8-docs/testing/MATRIX.md-approved`, `A8-docs/testing/PLAN.md-approved`, `A8-docs/testing/REPORT.md-approved`, and the not-run checks; raw `docs/testing/EXECUTION-LOG.md`.
- **Impact:** The master record understates approval by 38 scenarios and can cause duplicate work or a wrong release count. It does not falsely claim a PASS.
- **Recommendation:** Parent updates MATRIX/REPORT/PLAN/FINDINGS from the execution log. No agent may edit master status.

### F-02 — Per-stage report headers are stale (S2, audit gap)

- **Observation:** S3-R1, S4, S5, S6 and S7 report headers still say “Parent disposition: PENDING” (S6 also says 9 provisional PASS) while the execution log records accepted/partial. S4's footer contains the later acceptance, so the file contradicts itself.
- **Evidence:** audit findings `S10-A7-S3-R1`, `S10-A7-S4`, `S10-A7-S5`, `S10-A7-S6`, `S10-A7-S7`; reports vs `EXECUTION-LOG.md`.
- **Impact:** A reader of an individual report can reach the opposite disposition from the master log. This is a traceability defect, not a product defect.
- **Recommendation:** Parent adds a final disposition line to each report (or keeps the historical header and points to the log). Do not rewrite accepted results.

### F-03 — S8-R1 is not all-PASS because S8-03 and S6-05 use stale harness expectations (S1, audit gap; not a product defect)

- **Observation:** S8-R1 reports S8 **7 PASS / 1 FAIL / 1 BLOCKED** (S8-03 FAIL) and S6 **8 PASS / 1 FAIL** (S6-05 FAIL). The failures are caused by the harness, not the fixed product:
  - `scripts/testing/s8-qualify.mjs:1423` asserts the static blocked-JS state is `loading`; after the authorized fix it is correctly `failed` with a readable message.
  - `scripts/testing/s6-cases-a.mjs:774` asserts `document.scripts.length <= 1`; the fixed site has `bootstrap.js` + `assets/app.js` (two legitimate scripts).
- **Independent evidence:** P4 confirms the injection payload is inert and exactly the two legitimate scripts exist; P6 confirms the blocked-JS state is `failed` with disabled controls, no false gallery/preview, and the boot-throw path is equivalent. These checks pass.
- **Evidence:** `out/qualification/S10/results.json` checks P4/P6; `out/qualification/S8-R1/s8/artifacts/s8-03-static-nojs.json`; `out/qualification/S8-R1/s6/reports/S6-05.json`; S8-R1 report sections “S8-03 FAIL” and “S6-05 FAIL”.
- **Impact:** S8-R1 cannot be accepted as an all-PASS final site recheck. The product behavior is correct, but the required scenarios lack clean final-run evidence. This remains a release-qualification blocker until re-run, not a product defect.
- **Recommendation:** Apply the already-tracked harness fix at `7ac425d` (or an equivalent reviewed correction), then run S8-03 and S6-05 in a fresh sandbox, preferably the full S8/S6 suites, and record new totals. The S8-R2 attempt using `7ac425d` stopped at prepare with ENOSPC and produced no result, so it cannot substitute.

- **Observation:** S3-R1's report says the one-character mutation is rejected by the comparator. The control script hashes the original and mutated strings and checks `mutated !== golden`; it never calls the golden comparator or the package's rendered-output comparison. Any one-byte change necessarily changes a SHA-256, so the control is vacuous.
- **Evidence:** `scripts/testing/s3-controls.mjs` lines 144–148; `docs/testing/evidence/S3-R1.md:82`; raw `out/qualification/S3-R1/.../out-controls/controls-final.json`.
- **Impact:** The report's “all five controls detected” claim overstates NC5. The package golden itself is independently verified by S10 P1, so this is a control-evidence gap, not a product failure.
- **Recommendation:** Replace NC5 with a mutation passed through the real golden comparator, re-run the control and update the report. Do not count the current NC5 as comparator sensitivity.
